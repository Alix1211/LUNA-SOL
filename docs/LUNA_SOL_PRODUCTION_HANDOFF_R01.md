# LUNA SOL · 루나솔
## 완성형 게임 제작 착수 보완 지침 R01
**작성:** 2026-11-27  
**상태:** 제작 지시 기준. 게임 시스템 마스터 R01과 CORE GAMEPLAY R02를 폐기하지 않고 보완한다.  
**목적:** 이제 새 기획서를 반복 작성하지 말고 실제로 **처음부터 끝까지 즐길 수 있는 게임**을 제작한다. 사용자에게 중간 테스트 업무를 반복 전가하지 않는다.

> **가장 중요한 제작 조건:** 이 프로젝트는 상용 출시를 준비하는 팀의 반복 검증 프로젝트가 아니라, 개인이 **완성된 게임을 직접 즐기기 위한 프로젝트**다. 제작 과정에서 플레이 경험과 스포일러를 소모시키면 게임이 완성되어도 사용자는 흥미를 잃는다. AI가 제작·점검·수정의 주된 노동을 맡고, 사용자는 드물게 필요한 주요 디자인 판단과 완성본을 확인한다.

## 1. 적용 원칙과 충돌 해결

1. 게임의 중심은 가구 제작·실제 배치, 방 → 집/성 → 마을 → 왕국의 누적 복원과 생활·경제, 드래곤 돌봄·성장, 탐험과 90화 드라마의 **상호 강화**다.
2. 퀘스트는 지시형 심부름 목록이 **아니지만**, 단순한 장식이나 보상으로만 취급해서도 안 된다. **복원→퀘스트 해금, 퀘스트→긴 제작 준비, 퀘스트 완료→길·공간·시설 해금**이 모두 가능해야 한다.
3. 기존 90화의 사건, 캐릭터, 주요 관계, 등장 순서, 드래곤의 탄생·각성 조건, 복선과 결말은 유지한다. 필요 제작 미션의 수량과 경로는 시스템에 맞춰 재해석한다. 원본 대본을 임의로 고치지 말고 데이터 매핑과 별도의 수정 제안으로 관리한다.
4. 게임의 시스템 디렉션은 \`LUNA_SOL_CORE_GAMEPLAY_SYSTEM_R02.md\`와 \`LUNA_SOL_GAME_SYSTEM_MASTER_R01.md\`, 경제 수치는 \`LUNA_SOL_GAME_BALANCE_R01.md\`, 디렉터 결정 보류는 \`LUNA_SOL_DIRECTOR_DECISIONS_R01.md\`를 참조한다. **기존 문서 안에서도 확정/제안/미검증을 구분**한다.
5. 6×6 공용 보드, 작업력, 에너지, 가구의 배치 범위, 드래곤 성장 점수는 **검토 중인 권고값이지 확정 사양이 아니다**. 기기와 게임 흐름에 더 적합한 안이 있으면 근거를 기록하고 채택한다.
6. AI는 사용자 말을 무조건 복창하지 않는다. 다만 사용자가 말한 방향을 0/1의 극단적인 설계 변경으로 해석하지 않는다. **시스템 균형을 유지하며, 중요한 갈등은 판단 근거와 대안을 함께 보고**한다.

## 2. 당장 보완하여 구현할 게임 콘텐츠 (별도의 장기 문서 집필로 지연하지 말 것)

### A. 공간 복원과 꾸미기: 첫 방에서 왕국까지
- **공간 마스터 데이터:** 지역 ID, 공간/방 ID, 진입 조건, 구조물·가구 설치 가능 영역, 필수 안전시설, 선택적 꾸미기 영역, 복원 전·중·후 렌더 상태, 주민/드래곤 이용 행동, 다음 공간 연결을 실제 데이터로 작성한다.
- **최초 생활 공간부터 실물 콘텐츠:** 의자, 탁자, 침대, 벽/바닥/창호·조명, 커튼·수납·장식 등. 물건마다 제작 계보와 조립 레시피, 외형, 설치 위치 후보, 실제 이용 행동을 갖는다. 원본 EP001에서 이미 놓인 물건과 충돌하지 않게 기존 공간 상태를 확인한다.
- 공간 복원은 퍼센트나 배경 전환만으로 완료되지 않는다. 만들어진 가구의 **고유 소유·위치·변형·교체**, 실제 방의 변화, 다음 행동이 저장되어야 한다.
- **가구·건물·공간의 수량과 단계별 총 콘텐츠 범위**를 실제 구현에 사용되는 데이터로 확정한다. 90화를 몇 개의 공간·시설·새 행동이 지탱하는지 확인한다. 빈 공간을 동일 작업 목록으로 복제해 채우지 않는다.
- 일반 가구의 선택적인 재배치와 장식 변화가 시각적으로 충분히 보이게 한다. 완전 자유 배치가 한 손 터치에 맞지 않으면 넓은 후보 자리+방향+소품 조합으로 다양성을 준다. 고정 구조물의 안전 조건은 유지한다.
- 성과 마을의 복원에는 주민 입주, 기능 해금, 통행, 생산처, 방문·이용 동작 등 **새로운 생활 활동**이 이어져야 한다.
- **아트 원칙:** 공간의 구도/캐릭터 외형/아이템 아트는 일관성을 유지한다. 단순 플레이스홀더, 도형 UI, 중복 배경을 완성품으로 오인시키지 않는다. 실제 아트가 없는 부분은 결손으로 기록하고 제작한다.

### B. 머지와 생활 경제
- 기존 머지2/생산기/제작/조립/보관함/주문/판매/골드 흐름을 **끝까지 플레이 가능한 하나의 경제**로 만든다.
- 공용 보드/보드 분할은 기존 대안 분석을 이용해 결정하고, 화면 전환·터치 수·혼잡·중후반 확장성을 검증한다.
- 제작 계보별 **생산기·등급·조립법·해금·주요 사용처**를 전 지역의 콘텐츠와 연결한다. 가구, 주민 의뢰, 드래곤 용품, 이동수단이 같은 재료를 활용하되 각 분야의 개성을 잃지 않게 한다.
- 0골드, 기본 에너지 고갈, 보드 만석, 생산기 수납, 필수 자원 실수 판매 상황에서 **회복 가능한 경로**를 코드 레벨에서 검증한다.
- 무제한 무료 생산은 막힘 방지의 가안이지만, 의미 없는 탭 노동이 될 위험이 있다. **수급의 속도와 선택의 재미**를 확보한다. 단순 반복 횟수와 의도적 대기를 늘려 플레이 시간을 맞추지 않는다.
- 주문 수익·상위 물품 가치·골드 소진처의 불균형을 검증한다. 현재 밸런스 문서에 명시된 **작은 주문이 큰 주문보다 행동당 골드 효율이 높다는 문제**를 해결할 선택/보상 설계를 구현한다. 높은 주문은 단순 골드 외 도면·장식·특수 부품·새 공급처 등으로 구분할 수 있다.
- 사용자가 퀘스트를 미뤄도 주문, 시설, 꾸미기, 드래곤의 생활 순환이 멈춰서는 안 된다.

### C. 드래곤 육성: 숫자보다 살아 있는 행동
- 드래곤별 개별 거처(둥지/침구/조명/환경), 음식과 선호, 놀이·장난감, 목욕·손질, 휴식, 관계, 행동 변화와 성장 시각화를 갖춘다.
- 머지로 만드는 것은 드래곤 자체가 아니라 **숙소·먹이·용품·시설**이다. 살아 있는 개체 합성·생명력 추출·강제 계약 금지.
- 기존 친밀도 +1/+2, 단계 6/14 등은 검토용 예시일 뿐, 이 수치를 몇 번 눌러 성장시키는 것이 메인 콘텐츠가 되면 안 된다.
- **각 성장 단계에서 새로 등장하는 행동**, 거처의 변화, 취향 발견, 다른 드래곤과의 상호작용, 탐험/생활 이벤트와 연결되는 실제 콘텐츠를 정의·제작한다. 개체별 차이는 숫자 스킨 바꾸기가 아니어야 한다.
- 드래곤이 거절하거나 쉬어도 플레이어가 수동으로 대기하거나 벌점을 받게 하지 않는다. 강제 출석·굶주림 벌점·현실시간 성장 잠금 금지.
- 부화 전 알, 부화 후 유체, 성장체, 수호룡 성격별 예외를 시나리오 원본과 맞춰 처리한다. 모든 드래곤에 동일 유아 성장 단계를 강제하지 않는다.
- 드래곤이 없어도 기본 게임이 돌아가고, 새 드래곤이 등장하면 게임에서 **실제로 할 일이 늘어나는지** 확인한다.

### D. 탐험·퀘스트·해금의 양방향 연결
- 스토리 사건의 발생 조건과 준비 요건(이동수단·시설·자재·지도·인물), 완료 결과(길·지역·도면·거처·NPC)를 데이터로 연계한다.
- **장기 준비는 실물 제작/부분 조립/중간 외형 변화**를 포함한다. 배를 만들어 떠난다면 제작한 배가 보이고, 조립 진행을 저장하며, 출발 후 실제 경로가 열린다.
- 어떤 퀘스트는 작업 없이 즉시 완료될 수 있고, 다른 퀘스트는 수십 분의 준비가 필요할 수 있다. 임의로 모든 퀘스트에 3가지 제작 조건을 끼워 넣지 않는다.
- 새로운 지역의 해금 시점과 재료 공급처의 선후 관계, 출발·귀환 경로의 유효성, 스토리 플래그 충돌을 실제 데이터와 검증기로 점검한다.
- 메인 사건 준비 중에도 생활·가구·드래곤·주문 등 다른 목표를 자유롭게 선택한다.

## 3. 콘텐츠 범위와 완성 기준 (가짜 완성 금지)

- **목표는 본편 콘텐츠를 즐길 수 있는 완성형 빌드**다. 첫 방·첫 퀘스트만 플레이되는 MVP, 메뉴가 작동하지 않는 데모, 구현되지 않은 지역의 그림만 연결한 빌드를 최종본으로 보고하지 않는다.
- 8부 90화는 스토리 범위다. 30~45시간은 목표이며, **머지 클릭 수만 늘려 억지로 맞추지 않는다**.
- 전반·중반·후반의 공간, 시설, 제작 계보, 반복 주문, 드래곤의 생활 콘텐츠가 연동되어야 한다. 설계가 끝난 부분부터 내부적으로 제작해도 좋지만 **사용자에게 매번 테스트판 승인을 요구하지 않는다**.
- 반복 가능한 데이터 생성은 활용하되 지역별 모습, 기능, 의뢰 목적, NPC 행동이 천편일률적이어서는 안 된다.
- 원본 대본과 최신 통합 자료 중 **서로 모순되는 파일/규칙은 기록한 뒤 최신 제작 기준과 사용자의 핵심 디렉션을 비교**한다. 시나리오 내용을 임의로 개편하지 않는다.
- 모든 콘텐츠를 한 번에 구현할 수 없으면 **어디까지 구현됐고 무엇이 미완성인지 정직하게 표시**한다. 구현 못 한 것을 구현했다고 보고하거나 조잡한 대체물을 최종본으로 둔갑시키지 않는다.

## 4. 사용자 참여 최소화와 '플레이 경험 보호'

### 반복해서는 안 되는 진행
> 사소한 MVP 제작 → 사용자에게 설치/테스트 요구 → 짧은 확인 → 새 설계 변경 → 또 설치/테스트 → 동일한 지역·이벤트 반복 노출.

### 제작팀의 기본 작업 방식
1. 기획 문서 5종과 기존 90화 대본, 이미지·비주얼 가이드를 읽고 **내부 작업 항목과 의존성**을 구성한다. 사용자가 계획서를 다시 작성하게 하지 않는다.
2. 내부적으로는 기능별로 구현·자동 검증·수정해도 된다. **단계별 코드 검증은 필수지만 사용자를 무급 QA로 쓰지 않는다.**
3. 문법 검사, 데이터 참조 검사, 90화 선행조건 그래프 검사, 아이템 획득/소모 가능성 검사, 주문 수익·중복 보상·저장/복구, 0골드·막힘·드래곤 상태·화면 전환 테스트를 작업자가 수행한다.
4. 가능하다면 브라우저 자동화/실기기 에뮬레이터로 탭·합성·이동·조립·드래곤 행동·엔딩과 세이브를 재현한다. 가능한 자동화 범위를 보고하며 **자동 검사가 재미를 입증한다고 주장하지 않는다**.
5. 사용자는 **대형 미감·연출·게임 정체성 갈등처럼 판단이 꼭 필요한 경우에만** 개입시킨다. 그때도 2~3개의 대안을 근거와 함께 한꺼번에 제시한다. 사소한 버튼/수치/툴 선택마다 허가를 요구하지 않는다.
6. 플레이의 재미와 스토리 스포일러를 보호한다. 90화 주요 반전·엔딩·드래곤 등장 이벤트를 사용자에게 불필요하게 보여주거나 미리 전부 테스트시키지 않는다. 사용자는 원하면 상세 내용을 볼 수 있다.
7. 제작 마무리에는 **실제 설치·구동 가능한 HTML부터** 제공하고, APK까지 요청/계획 범위에 포함되어 있다면 별도로 빌드한다. 서명키·패키지명·저장 키를 임의로 바꿔 기존 세이브를 소실시키지 않는다.
8. 배포 자료에는 **GitHub 저장소/브랜치/커밋/최종 HTML·APK의 정확한 경로 및 접근 가능한 링크**, 자동 테스트 결과, 알려진 결함, 저장 호환 여부를 명시한다.

### 정말로 필요한 사용자 확인
- 기존 세계관·주인공·엔딩을 바꿀 만큼 중대한 스토리 변경.
- 핵심 게임 플레이를 다른 장르로 바꾸는 결정.
- 기존 저장과 호환되지 않는 변경·강제 초기화.
- 주요 아트 방향의 근본적인 변경.

**일상적인 테스트, 세부 수치 비교, 렌더 오류 수정, 보드 사이즈 임시 실험은 개발자/AI의 내부 업무다.**

## 5. 제작 마감 전에 통과할 필수 검수

| 분야 | 반드시 통과할 결과 |
|---|---|
| 첫 방 | 의자·탁자·침대 등 가구 제작·조립·배치·교체, 공간 변화와 가구 이용 동작 |
| 공간 확장 | 방→집/성→마을→주요 지역이 실제 기능·동선·주민 행동을 갖고 연결 |
| 게임 루프 | 스토리 일시정지 후에도 주문·생산·합성·가구·경제가 의미 있게 작동 |
| 드래곤 | 해금 전/후, 개별 거처·음식·놀이·성장, 다른 반응·행동 실물 구현 |
| 탐험 | 장시간 이동 준비의 중간 조립이 남고, 여행·새 길·귀환이 실제 연결 |
| 90화 | 주요 사건·인물·드래곤 출현 순서·복선·엔딩의 상태 연결이 깨지지 않음 |
| 경제 | 0골드·생산 제한·보드 만석·매입/매각 차익·고급 주문 가치 점검 |
| 저장 | 중단 후 재개·재설치/버전 갱신·백업/복구, 중복 지급 방지 |
| 조작 | 가로 태블릿/휴대폰, 오른손 검지 한 손 입력, 정밀 드래그·핀치 필수 없음 |
| 품질 | 완성되지 않은 버튼·가짜 진행·중복 CG·깨진 컷인·메모리/성능 문제 점검 |
| 전달 | 최종 HTML 링크, APK가 만들어졌다면 링크, 브랜치·커밋·저장 호환·알려진 문제 기록 |

**주의:** 이 검수표는 AI에게 완성 검증을 수행하라는 기준이지, 사용자가 각 항목을 여러 차례 수동 플레이하라는 요청이 아니다. 사람이 실제로 느끼는 재미와 미감을 자동화가 100% 보장하지는 않으므로 그런 한계를 숨기지 않는다.

## 6. 작업 순서: 완성형 본편 제작으로 전환

1. 기존 기획·시나리오·비주얼 자료를 단일 구현 데이터와 작업 순서로 통합. 새 기획서 양산보다 **게임 코드·콘텐츠·아트·실행 가능한 빌드**를 우선.
2. **기반 엔진·자원·저장·화면/공간 배치·생산/조립·경제·드래곤 상태·퀘스트 조건 시스템**을 함께 설계하고 제작.
3. 내부적으로 첫 방의 실물 가구·주문·드래곤 전후·탐험 준비가 서로 연결되는지 테스트해 **시스템이 이후 콘텐츠를 담을 수 있는지** 확인. 사용자에게 반복 제공하지 않음.
4. 같은 시스템을 기준으로 **성→마을→왕국의 공간 콘텐츠와 90화 사건, 드래곤 행동, 아이템·주문·아트**를 데이터 중심으로 실제 채움.
5. 자동 테스트·재현·중요 결함 수정을 반복. 사용자의 플레이 소진을 피하고 필요한 결정만 모아서 보고.
6. 완성 콘텐츠의 실제 동선·저장·성능·그래픽을 검수한 뒤 배포 가능한 **본편 결과물**을 전달.

**무조건 '한 번에 코드를 작성하라'는 뜻이 아니다. 개발 내부에는 적절한 중간 빌드와 검증이 필수다. 다만 사용자에게 매번 불완전한 결과물을 테스트하도록 요구하지 말라는 뜻이다.**

## 7. 사용자에게 보고할 것과 보고하지 말 것

- **보고:** 결과물 파일과 GitHub 링크, 이번에 실제 완성된 범위, 미구현 및 오류, 저장 호환, 결정을 필요로 하는 중요한 항목.

- "완성", "검증됨"이라는 표현은 실제 파일과 재현 가능한 근거가 있는 범위에서만 사용한다.

## 8. 최종 제작 메시지
